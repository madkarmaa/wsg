# AGENTS.md

WSG is a WhatsApp Web client mod: a Manifest V3 Chromium extension built with [Extension.js](https://extension.js.org). Its architecture closely follows [Vencord](https://github.com/Vendicated/Vencord)/[Equicord](https://github.com/Equicord/Equicord), since WhatsApp Web, like Discord, is a React app. When in doubt about how something should work, look at how Vencord does it.

## Commands

Use `bun`.

- `bun run dev`: watch mode. Launches Chrome with a persistent profile on web.whatsapp.com (log in once).
- `bun run build`: typecheck, then production build into `dist/chrome`.
- `bun run build:zip`: same, plus a store zip.
- `bun run typecheck`: `tsc --noEmit`. Must pass before any change is done.
- `bun run format`: Prettier (4 spaces, single quotes, width 100, no trailing commas).

`extension-env.d.ts` is generated by Extension.js (it declares `IS_DEV` from `define` in `extension.config.mjs`). It is committed so typechecking works on a fresh clone.

## How it works

- `src/manifest.json` declares one content script, `src/index.ts`, with `world: "MAIN"` and `run_at: "document_start"`. Extension.js calls its default export before any WhatsApp script runs. In production the script is a static manifest entry. In dev it is registered by Extension.js's service worker, which still runs it at `document_start`.
- WhatsApp uses Meta's module system. Modules are defined with `__d(id, deps, factory, flags)` (sometimes `define`), have stable human readable ids (`WAWebABProps`, `WDSSwitch.react`, ...), and are tracked in `require('__debug').modulesMap`.
- `src/modules/patcher.ts` intercepts `__d`/`define` and wraps every factory, preserving `factory.length` because WhatsApp's loader reads it. On a factory's first call it applies matching patches to the factory source, runs it, then notifies `waitFor` subscribers synchronously, before any other module can use the exports.
- WhatsApp's CSP forbids `eval`. Patched factories are evaluated by `src/utils/evaluate.ts` as inline scripts carrying the page's nonce, which run synchronously on insertion. Never use `eval`/`new Function` in page code: besides failing, CSP violations are reported to WhatsApp with a sample of the code.
- `src/api/PluginManager.ts` registers the patches of enabled plugins before WhatsApp loads, and starts plugins at their `startAt` stage (`Init`, `DOMContentLoaded`, `ModulesReady`).
- Settings live in `localStorage` under `WSG_Settings`. They have to be readable synchronously at `document_start`, since they decide which patches are registered. MAIN world scripts can't use `chrome.*` APIs.
- `window.WSG` (`src/WSG.ts`) exposes everything. Patches reference their plugin as `$self`, which expands to `WSG.Plugins.plugins["Name"]`.

## Writing plugins

Plugins are discovered from `src/plugins/<name>.ts(x)`, `src/plugins/<name>/index.ts(x)` and the same inside `_api/` and `_core/`. The default export must be `definePlugin({...})`. Use `Devs` from `@utils/constants` for authors.

```ts
export default definePlugin({
    name: 'MyPlugin',
    description: 'What it does, as one sentence.',
    authors: [Devs.madkarma],
    patches: [
        {
            module: 'WAWebSomeModule', // target by id (preferred), and/or `find` by source substring/RegExp
            replacement: {
                match: /(\i\.default=)\i(?=\}$)/, // \i matches any identifier
                replace: '$1$self.Replacement' // $self is this plugin object
            }
        }
    ],
    Replacement() {
        /* ... */
    }
});
```

- Patches are matched against the factory source as WhatsApp ships it (minified). Find it with `WSG.Modules.getModuleSource(id)` or `require('__debug').modulesMap[id].factory`, before the module loads. Match on stable strings (module ids passed to `o("...")`/`r("...")`, prop names, string literals) and use `\i` for minified identifiers.
- A patch is applied once and then dropped unless `all: true`. Use `group: true` when replacements depend on each other. A replacement with no effect logs `Patch by X had no effect`, so check the console.
- Plugins with patches need a reload to toggle (`requiresRestart` defaults to true). Set it explicitly for plugins whose effect is read at boot, such as AB prop overrides.
- `startAt: StartAt.Init` runs before WhatsApp's code. The default `ModulesReady` runs once React and ReactDOM have loaded.
- Settings: `definePluginSettings({...})`, assigned to `settings`. Read them with `settings.store`, or in components with `settings.use(['key'])`.
- `managedStyle` is CSS injected while the plugin runs. Prefix classes with `wsg-` and use WhatsApp's `--WDS-*` CSS variables for colors.
- A/B gated features: depend on `ABPropsAPI` and call `setABPropOverride(name, value)` in `start`.

## Finding WhatsApp internals

- `findModule<T>(id)`: exports by id. It initialises modules that are defined but not yet required, and returns `null` if WhatsApp hasn't downloaded the module yet.
- `requireModules(...ids)`: downloads and loads modules (WhatsApp's `requireLazy`). Call it before rendering lazily loaded components or icons. Many WhatsApp render paths are memoized and render only once, so a missing component stays missing.
- `waitFor(idOrFilter, cb)` / `waitForModule`: runs right after the module's factory, before anything else uses it.
- `find`, `findAll`, `filters.byProps/byCode/byDisplayName/componentByCode`, `findModuleIds(...code)`, and the `*Lazy` variants (proxies that resolve on first use).
- `@modules/common`: `React`, hooks and `ReactDOM` are live bindings to WhatsApp's own React. It also has typed WDS components (`MenuItem`, `Switch`, `Button`, `Text`, `ConfirmPopup`, `Toast`, `findIcon('IcName')`) and the `ModalManager`, `ToastManager` and `Cmd` managers.
- WhatsApp components have `displayName`s like `S [from WAWebIntroPanelV2.react]`.

## React and JSX

WSG does not bundle React. `react/jsx-runtime` is aliased (in `extension.config.mjs`) to `src/utils/jsxRuntime.ts`, which forwards to WhatsApp's React. Only use `import type` from `react`. Runtime values come from `@modules/common`. JSX may only render after React has loaded, which is always true for anything rendered by WhatsApp.

## Type safety

Strict typing is the top priority.

- Never use `any`. Module exports and other untrusted values are `unknown`: narrow them with the guards in `@utils/guards`, or give finders an explicit type parameter.
- When a cast is unavoidable, use `as unknown as T` or a direct cast from `unknown`, with a comment saying why it is sound.
- Avoid non-null assertions. Lazy helpers accept factories returning `null | undefined`.

## Testing in the browser

Test changes against real WhatsApp Web through the chrome-devtools MCP (`.mcp.json`):

1. Chrome must run with `--enable-unsafe-extension-debugging` (e.g. in `~/.config/chrome-flags.conf`) and remote debugging enabled at `chrome://inspect/#remote-debugging`. The MCP needs `--categoryExtensions`.
2. `bun run build`, then `install_extension` with the absolute path of `dist/chrome`. After later rebuilds, `reload_extension` and reload the WhatsApp tab.
3. Verify through `evaluate_script`:
    - `WSG.Modules.patchedModules`: applied patches and the plugins that applied them.
    - `WSG.Modules.patches`: patches still waiting for their module (expected only for modules that haven't loaded yet).
    - `Object.values(WSG.Plugins.plugins).filter(p => p.started)`.
    - WSG warnings and errors in `list_console_messages`.
4. The account is the user's real one. Prefer targeted `evaluate_script` queries over `take_snapshot` (the snapshot dumps chat names and messages). Never send messages or change account state. Restore any settings you changed (`localStorage.removeItem('WSG_Settings')` resets to defaults).

`evaluate_script` bypasses CSP, so code that works there may still be blocked in a content script.

## Conventions

- Commits follow Conventional Commits (`feat:`, `fix:`, `refactor:`, `chore(scope):`).
- Match the surrounding code: small modules, named exports (except plugins), comments only where intent isn't obvious.
- Don't add documentation or report files that merely describe completed work.
